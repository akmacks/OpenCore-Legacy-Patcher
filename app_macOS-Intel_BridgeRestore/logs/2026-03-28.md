## Late Session Addition — 2026-03-28 ~21:30

### Root Cause of TB Bridge Drop IDENTIFIED

**Observation from user:** ARD shows mini with self-assigned IP 169.254.51.63.
IP Broadcaster shows bridge0: 192.168.2.2 correctly, WAN offline.

**Diagnosis:**
- 169.254.51.63 is an APIPA address on en0 (BCM5722 Ethernet)
- BCM5722D.kext not loading → en0 hardware present, DHCP fails → macOS assigns APIPA
- macOS `configd` enters DHCP re-probe loop on en0 (interval ~30s)
- Re-probe loop disturbs network stack → bridge0 assignment resets briefly
- This is the exact mechanism behind the 28-80 ping drop window

**Evidence chain:**
1. ARD uses highest-priority interface → chose en0 (169.254.51.63) over bridge0
2. IP Broadcaster shows bridge0: 192.168.2.2 ✅ — bridge itself is correct
3. Drop interval matches configd probe retry schedule precisely

**Fix added to app:**
- `run_diag`: new L2b check detects APIPA on non-bridge interfaces, warns with fix command
- `_restore_as_client`: auto-runs `networksetup -setnetworkserviceenabled "Ethernet" off`
  if en0 has 169.254.x.x → stops configd probe loop → bridge stabilises

**Permanent fix path:**
1. Apply OCLP root patches on mini
2. Reboot → BCM5722D.kext loads → en0 gets real IP 192.168.0.111
3. configd satisfied, probe loop ends, bridge permanent stable

**To try immediately on mini:**
```bash
sudo networksetup -setnetworkserviceenabled "Ethernet" off
```
This should make the bridge stable without rebooting.
