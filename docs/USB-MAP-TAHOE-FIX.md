# USB-Map Key Name Fix for Tahoe (IOUSBHostFamily 1.2)

**Status:** ✅ Fixed — Session 19, 2026-04-13  
**Affects:** All Intel EHCI USB controllers on non-T2 Intel Macs running macOS Tahoe 26.x  
**Confirmed hardware:** Macmini5,3 (Sandy Bridge, PCH EHCI, macOS Tahoe 26.4 / XNU 25E246)  
**Fix type:** EFI/OC/Kexts/USB-Map.kext Info.plist key name update  

---

## Symptom

After OCLP root patches applied on Tahoe:

- **All USB ports have no power** — devices do not charge, no 5V on any port
- Both direct USB ports and hub-connected ports are dead
- No USB devices appear in System Report or `ioreg -p IOUSB`
- `AppleUSBEHCIPCI` shows `registered, matched, active` in IORegistry — driver loads correctly
- `kextstat` shows all USB kexts loaded at version 1.2, no errors
- `controller-statistics` in IORegistry shows:
  ```
  kPowerStateOn: 4ms (0%)
  kPowerStateSuspended: ~uptime_ms (99%)
  ```

The EHCI controllers initialise briefly then immediately enter D3 power management suspend, which cuts VBUS (5V) to all ports.

---

## Root Cause

### Background

OCLP root patches inject `AppleUSBEHCI` and `AppleUSBEHCIPCI` kexts into the sealed system snapshot to provide Intel EHCI USB 2.0 controller support on Tahoe, which does not include these kexts natively (it ships only Apple Silicon / embedded USB drivers).

A companion kext, `USB-Map.kext`, is injected via EFI/OC to provide `AppleUSBHostMergeProperties` personalities that configure each EHCI controller's port topology — port count, port type (internal/external), and port numbers.

### The Problem: Key Name API Change in Tahoe

Tahoe's `IOUSBHostFamily` 1.2 introduced new key names for USB port personality data. The old (pre-Tahoe) key names are no longer read by the EHCI driver:

| Old key (pre-Tahoe) | New key (Tahoe 1.2) |
|---|---|
| `UsbConnector` | `usb-port-type` |
| `port` (data, port number) | `usb-port-number` (data, same encoding) |

The OCLP build system correctly generates a `USB-Map-Tahoe.kext` with the new key names. However, the EFI deployment step was using `USB-Map.kext` (old key names) instead of `USB-Map-Tahoe.kext`.

### Failure Chain

1. `AppleUSBEHCIPCI` loads and matches EHC1 (`pci8086,1c26`) and EHC2 (`pci8086,1c2d`) ✓
2. `USB-Map.kext` injects `port-count: 1` and one port entry per controller ✓
3. Port entry uses `UsbConnector` / `port` keys — **NOT recognised by Tahoe EHCI 1.2 driver**
4. Driver creates **zero** `AppleUSBEHCIPort` instances (confirmed: `AppleUSBEHCIPort=0` in IOKitDiagnostics)
5. With no ports, both controllers have no USB activity to service
6. Controllers enter D3 power management suspend after ~4ms
7. D3 suspend deasserts port power (VBUS) on Intel PCH EHCI — **all USB ports lose 5V**

### Why This Is Silent

The EHCI driver does not log a warning when it encounters unknown port personality keys. It simply does not create port objects, leaving the controller with nothing to drive.

## Fix Applied (Session 19)

The fix replaces the old-format `USB-Map.kext/Contents/Info.plist` with the Tahoe-format equivalent already generated by OCLP's build system.

### Manual Fix (EFI already deployed)

```bash
# Mount EFI
sudo diskutil mount disk0s1

# Copy Tahoe-format Info.plist over old-format
cp ~/Documents/GitHub/OpenCore-Legacy-Patcher/Build-Folder/OpenCore-Build/EFI/OC/Kexts/USB-Map-Tahoe.kext/Contents/Info.plist \
   /Volumes/EFI/EFI/OC/Kexts/USB-Map.kext/Contents/Info.plist

# Reboot
sudo reboot
```

### Key Format Difference

**Old (broken on Tahoe):**
```xml
<key>PRT1</key>
<dict>
    <key>UsbConnector</key>
    <integer>255</integer>
    <key>port</key>
    <data>AQAAAA==</data>
</dict>
```

**New (Tahoe IOUSBHostFamily 1.2):**
```xml
<key>PRT1</key>
<dict>
    <key>usb-port-number</key>
    <data>AQAAAA==</data>
    <key>usb-port-type</key>
    <integer>255</integer>
</dict>
```

The data values are identical — only the key names changed.

## Relationship to UHCI ABI Mismatch

The UHCI (USB 1.1 companion) ABI issue is a **separate** problem — `AppleUSBUHCI` and `AppleUSBOHCI` from macOS 12.6 have a vtable count mismatch with Tahoe's `IOUSBHostFamily`. These kexts cannot load.

However, with `kUSBCompanion: false` set in USB-Map, the EHCI controller operates without UHCI companions and handles full-speed (12 Mbps) and low-speed (1.5 Mbps) USB devices via its built-in **Transaction Translator (TT)**. This means:

- UHCI kexts do **not** need to load for USB 1.x functionality
- All speed classes (USB 1.0, 1.1, 2.0) work through EHCI TT
- `kUSBCompanion: false` is the correct setting and should be retained

## OCLP Pipeline Fix Required

The OCLP build system already generates both `USB-Map.kext` (old format) and `USB-Map-Tahoe.kext` (Tahoe format). The issue is in the EFI deployment step, which uses `USB-Map.kext` regardless of target OS.

**Required change in OCLP source:**

In the USB map generation / EFI build pipeline (likely `opencore_pkg.py` or `build_opencore.py`), when the target OS is Tahoe (macOS 26.x / XNU 25.x), the deployment should use `USB-Map-Tahoe.kext` instead of `USB-Map.kext`.

Alternatively, the USB map generator itself should detect the target OS and write the appropriate key names directly, eliminating the need for two separate kexts.

**Affected file (to investigate):**
```
opencore_legacy_patcher/sys_patch/kernelcache/
opencore_legacy_patcher/efi_builder/
```

Look for where `USB-Map.kext` is referenced in the EFI build path and add a Tahoe OS version check.

## Hardware Reference (Macmini5,3)

| Controller | PCI ID | ACPI Path | Ports |
|---|---|---|---|
| EHC1 | pci8086,1c26 | `/_SB/PCI0/EHC1@1d0007` | Internal hub → IR, wireless receiver, KB hub |
| EHC2 | pci8086,1c2d | `/_SB/PCI0/EHC2@1a0007` | Available for external devices |

USB topology: Both EHCI controllers connect through an internal hub on the motherboard. Physical USB ports on the rear panel are downstream of this hub, not direct EHCI root hub ports. The USB-Map only needs to describe the single internal EHCI root hub port (UsbConnector=255 / usb-port-type=255) per controller.
