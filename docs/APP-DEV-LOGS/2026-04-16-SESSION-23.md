## 1. Problem Discovery

After Session 21's ACPI renames (`EHC1→EH01`, `EHC2→EH02`), the existing USB-Map.kext still had `IONameMatch` entries for `EHC1` and `EHC2`. Since macOS matches IOKit personalities by ACPI device name after rename, these merge properties **never matched** and were completely inert.

**Consequences:**
- No port type mapping applied (ports treated as unknown type)
- `kUSBCompanion=false` was never set on the active controllers
- The UHCI companion controllers (UHC2–UHC4, UHC6–UHC7) remain disabled (`_STA=0x09`)
- `AppleUSBUHCIPCI` instances = 0

**This was the #1 reason UHCI companion controllers aren't loading** — macOS doesn't need them when `kUSBCompanion=false` tells the EHCI driver to handle all speeds internally. But the kext was targeting the wrong names.

## 3. USB-Map.kext v1.1 Changes

### Fixed Issues:
1. **IONameMatch**: `EHC1` → `EH01`, `EHC2` → `EH02` (matches ACPI renames)
2. **port-count**: `1` (0x01) → `3` (0x03) for both controllers (each has 3 active ports)
3. **PRT2/PRT3 added**: Both external USB-A ports now explicitly mapped (type 0 = Type-A connector)
4. **PRT1**: Remains type 255 (internal) — covers the internal hub

### Port Type Values:
- `0` = Type-A connector (external rear USB ports)
- `255` = Internal (hub, Bluetooth, IR Receiver)

### Key Design Decision:
`kUSBCompanion=false` remains on both EHCI controllers. On Tahoe (Darwin 25.x), the UHCI companion model is legacy. The EHCI driver handles all speeds (LS/FS/HS) when `kUSBCompanion=false`, which is exactly what we want for:
- Full-speed mouse + keyboard (1.5 Mbps)
- Low-speed IR receiver
- High-speed hub devices

## 7. Decision: No SSDT-USB-MAP Needed (Yet)

The original Session 22 plan called for an SSDT to enable UHCI companions (set `_STA=0xF`). However, with `kUSBCompanion=false`, the EHCI controllers handle all USB 1.x devices internally. This means:

- UHCI companion controllers are **not needed** for current functionality
- The 5 disabled UHCIs (UHC2-4, UHC6-7) would only matter if we needed raw UHCI ports for specific devices
- On Tahoe, Apple's EHCI driver with `kUSBCompanion=false` already routes LS/FS traffic through the EHCI controller

**Recommendation:** Hold off on SSDT-USB-MAP until we have a specific device that requires direct UHCI access. Current USB stack is complete with just the kext fix.

## 8. Post-Reboot: USB-Map v1.1 Broke USB — Rollback to v1.0

**Result:** USB-Map v1.1 (EH01/EH02 IONameMatch, port-count=3, explicit PRT1/2/3) caused total USB failure:
- Only 1 `AppleUSBEHCIPort` instance created (was 6 with v1.0)
- Zero USB devices enumerated
- Both EHCI controllers stuck in suspended power state (`CurrentPowerState=2`, `DriverPowerState=0`)
- `kControllerStatIOCount=0` — no I/O processed at all

**Root cause analysis:**
When `AppleUSBHostMergeProperties` matches the controller name (EH01/EH02), it overrides ACPI port enumeration with explicit port definitions. The kext's `PRT1/PRT2/PRT3` definitions with `usb-port-type` values apparently conflict with how Tahoe's EHCI driver creates port objects internally. The driver reads these merge properties and then doesn't create the expected `AppleUSBEHCIPort` child objects.

With v1.0 (IONameMatch=EHC1/EHC2, which doesn't match the renamed devices), the merge properties are inert. The EHCI driver falls back to ACPI enumeration (`_UPC`/`_PLD` from the DSDT), which correctly creates all 6 port objects.

**Action taken:**
- Rolled back to USB-Map.kext v1.0 (EHC1/EHC2 IONameMatch = inert)
- APFS snapshot before rollback: `2026-04-16-161511`
- All 3 USB devices restored after reboot
- 6 `AppleUSBEHCIPort` instances confirmed working

**Lesson:** On Tahoe (Darwin 25.x), `AppleUSBHostMergeProperties` with explicit port definitions for renamed EHCI controllers **breaks port enumeration**. The ACPI fallback path is the correct mechanism. The kext should remain inert (targeting the pre-rename names EHC1/EHC2).

**Future approach:** If we need to set `kUSBCompanion=false` or adjust port types, we should use an SSDT with `_UPC`/`_PLD` methods in the ACPI namespace, NOT the merge kext. The merge kext's port definitions appear to override internal EHCI port creation in a way that's incompatible with Tahoe's driver.
